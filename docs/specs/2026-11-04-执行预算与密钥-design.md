# 执行预算与密钥（批次 B）

- 日期：2026-11-04
- 范围：refresh / replan 的查询方式与时间预算、密钥注入口径、replan 入参契约、执行预算口径表（本仓库数字的唯一事实源）
- 不在范围：界面改动（省心段的结构化行程入口是账本第 3 条）、多航线、ECS 部署、真实推送
- 上游：`docs/specs/2026-11-04-数据管道-design.md`（管道与闸门）、`docs/specs/2026-11-04-入口页与三段页-design.md`（两页与遗留风险）
- 一句话：把「agent 自己决定查几次」从两条慢路径上收回来——后端生成查询脚本、agent 只做判断，顺手把密钥口径与 replan 入参一次定死。

## 0. 本 spec 解决账本第 1 条的哪几件事

| 账本原文 | 本 spec 的结论 |
|---|---|
| replan 按类型给超时或压查询次数 | 两条都做：超时按类型分档 + 查询范围压到「当日 + 次日 + 可选火车」 |
| refresh 走命令模板 + 缓存 | 命令模板做（后端生成 `run-queries.sh`）；**缓存不做**，理由见决策 5 |
| `BAILIAN_API_KEY` / `FLYAI_API_KEY` 口径 | §5 一次定死：前者必需且缺了就失败，后者可选且决定要不要查火车 |
| replan 入参是否带结构化 `interruption.flight` | 带，可选字段，形状与快照里的 `interruption.flight` 完全一致 |
| 总纲与 §5 口径表 | **不建总纲**。仓库内从未定义过 D1–D4 / S0–S6 / R1–R13，为引用而造一份编号体系等于写一份没人读的文档。数字口径只在 §2 留一张表，账本与后续 spec 一律引用本 spec §2 |

## 1. 决策清单

| # | 问题 | 结论 | 理由 |
|---|---|---|---|
| 1 | 谁生成查询命令 | 后端。每条 job 目录里写一份 `run-queries.sh`，参数已展开成字面量 | 实测「请并发」无效（208s→217s）：模型不会把一句话翻译成一次 shell 调用，只会一轮一轮调工具 |
| 2 | 这算不算推翻「agent 决定怎么查」（数据管道决策 1） | 只推翻 refresh 与 replan 两条路径，discover 不变 | discover 要理解「只给了班次号」并反问，判断不能拿走；refresh/replan 要查什么在入参里已经完全确定，让模型再决定一次只是烧轮次 |
| 3 | 脚本负责到哪一步 | 只取原始输出，不解析、不排序、不算价 | 判断权仍归 agent，闸门仍是唯一裁判；脚本进代码后如果开始算最低价，等于后端偷偷调 flyai（违反决策 2） |
| 4 | replan 查什么 | 被打断日 + 次日各一次航班查询；注入了 `FLYAI_API_KEY` 再各加一次火车 | 与快照候选覆盖面一致；用户说「后天必须到」这类情况脚本不覆盖，由 summary 老实说明 |
| 5 | refresh 要不要价格缓存 | 不做 | flyai 单次真调用 0.6s，缓存省的是秒级；208s 花在模型轮次，不在查询。缓存放进提示词就绕开 `raw/`，闸门 3 必拒；要让旧价过关只能放宽闸门或伪造 raw，两条都比省 1 秒贵 |
| 6 | 超时 | 按类型分档：discover 90s、refresh 150s、replan 120s（每轮） | 现状一刀 300s 是照 175s 的旧 refresh 定的；脚本化后失败 = flyai 或没写文件，等 5 分钟没有意义 |
| 7 | 重试 | 只有 discover 保留 2 轮（第二轮带失败原因）；refresh / replan 各 1 轮 | 决策 11 的价值在「缺字段/结构错」这类可纠正错误，脚本化后基本不复现；旧快照不动已是安全兜底 |
| 8 | `BAILIAN_API_KEY` | 必需。缺失时 job 直接 failed，不重试；**不进 Joi** | 进了 Joi 会让 `pnpm test`、CI、纯前端开发在没有 key 的机器上起不来；运行期报错文案已经足够清楚 |
| 9 | `FLYAI_API_KEY` | 可选。只由后端在拼脚本时读一次：有则脚本多两行火车查询，无则提示词明写「不要查火车」 | 体验模式下火车价是 `1xx/5xx` 打码值，raw 里没有可用数字，模型为了凑一个能过闸门的价会反复重查——这正是 replan 跑不完的直接原因 |
| 10 | replan 入参 | `POST /api/replan { situation, flight? }`，`flight` 可选，给了就 5 个字段全给 | 界面不做，只定契约；账本第 3 条（省心段结构化入口）落地时不用再改一次接口 |
| 11 | 前端轮询上限 | 620s 不动 | 新最坏耗时 180s（discover 90×2），改它没有收益 |

## 2. 执行预算口径表（本仓库数字的唯一事实源）

| 项 | discover | refresh | replan |
|---|---|---|---|
| 单轮超时 | 90s | 150s | 120s |
| 轮数上限 | 2 | 1 | 1 |
| 最坏耗时 | 180s | 150s | 120s |
| 查询方式 | agent 自己调 flyai | `./run-queries.sh` | `./run-queries.sh` |
| flyai 查询次数 | 由 agent 决定 | 6（5 天逐天 + 当天指定班号）+ 火车 1（可选） | 2（当日 + 次日）+ 火车 2（可选） |
| 产物 | `offers.json` | `dataset.json` | `plan.json` |
| 价格缓存 | 无 | 无 | 无 |

其它既有口径（一并归口到这里，避免两处数字）：前端 `pollJob` 上限 620s；`cheapestDays` 的 10 分钟 `dayCache` 保留不动；`meta.mode` 仍由 raw 里是否出现「体验模式」判定。

实测基线（2026-11-04）：discover 21–50s、refresh 175–217s（脚本前）、flyai 单次真调用 0.6s、opencode 冷启动 1.7s、每轮固定重发约 10k token 上下文、一次「查询 + 落盘 + 回答」28s。

## 3. `run-queries.sh`

### 3.1 生成与写入

- 新文件 `apps/admin/src/modules/agent/query.script.ts`，导出 `planRefresh(watch, train)` / `planReplan(flight, train)` 生成 `QueryPlan`（查询清单 + 文件名规则），`buildScript(plan)` 生成 sh 文本并在这一步做参数白名单校验；
- `prepareJobDir(jobDir, input, script?)` 增加可选第三参：给了就写 `run-queries.sh` 并 `chmod 755`（skill 副本仍是 444，两者别混）；
- discover 不传脚本，目录形状与现在完全一致。

### 3.2 脚本形状（refresh，北京→上海 2026-11-06，班次 MF8561）

```sh
#!/bin/sh
set -u
cd "$(dirname "$0")"
flyai search-flight --origin '北京' --destination '上海' --dep-date 2026-11-06 --journey-type 1 --sort-type 3 > raw/flight-2026-11-06.json 2> raw/flight-2026-11-06.err
# … 2026-11-07 / 11-08 / 11-09 / 11-10 同上
flyai search-flight --origin '北京' --destination '上海' --dep-date 2026-11-06 --transport-no 'MF8561' > raw/watched-2026-11-06.json 2> raw/watched-2026-11-06.err
# 注入 FLYAI_API_KEY 时才有这一行
flyai search-train --origin '北京' --destination '上海' --dep-date 2026-11-06 --journey-type 1 > raw/train-2026-11-06.json 2> raw/train-2026-11-06.err
```

**逐条串行，不加 `&` 与 `wait`**：实际跑 6 条并发会撞 flyai 的 `429 Rate limit exceeded`，只放行 2 条；串行实测 3.2s（6 次查询），仍远低于 150s 预算。

replan 的脚本结构相同，只换成 `flight-<被打断日>` / `flight-<次日>`（+ `train-` 两条）。文件名规则一共三种，`watched-` 只出现在 refresh。

`.err` 文件不进闸门：`readRaw` 只收 `raw/*.json`（已核过实现），留着是给「缺 11-08 的报价」这类失败排查用。

### 3.3 安全：这是新增的注入面

参数来自用户输入（城市、班次号、日期）却要拼进 shell，必须在拼之前校验，非法即 `throw new Error` 让 job failed：

| 字段 | 允许的字符 | 长度 |
|---|---|---|
| 城市（origin / destination） | 汉字、字母、数字、空格、`·`、`-` | 1–20 |
| 班次号（transport_no） | 字母、数字 | 2–10 |
| 日期（date） | `YYYY-MM-DD` 且是真实存在的日期（parse 后回写等于原值——`Date.parse("2026-11-31")` 会顺延成 12-01，不能只靠它） | 10 |

单引号包裹 + 白名单里没有 `'`、`$`、反引号、`;`、换行，因此不存在二次展开。校验只写一处（`buildScript` 里），不散到 DTO——脚本是唯一的拼接点。

## 4. 提示词改动

### 4.1 refresh（`prompts/refresh.ts`）

- 删掉「这 5 次查询互不依赖，请在同一次 shell 调用里并发发起」整段，换成一句：「先跑一次 `./run-queries.sh`，它会把全部查询的原始输出写进 `raw/`，实测约 3 秒；**不要再自己调 flyai**」；
- 保留「三件事」的语义，但改成「从 raw 里取」：
  1. `raw/watched-<date>.json` → `watch.offers` 里那一条；
  2. `raw/flight-<date>.json`（5 份）→ 每天最低价 → `series`；
  3. `raw/flight-*` + `raw/train-*` → `interruption.candidates`；
- 加一句上下文纪律：「raw 单份约 9KB，逐天取最低价用 `node -e` 在 shell 里算好再写产物，不要把 6 份全文读进上下文」；
- 无 `FLYAI_API_KEY` 时追加：「本次没有注入 `FLYAI_API_KEY`，火车价会打码；不要查火车、不要写火车候选，在 `notes` 里说明」。

### 4.2 replan（`prompts/replan.ts`）

- 同样先跑脚本，禁止额外查询；
- 候选只能来自 `raw/flight-<当日>` 与 `raw/flight-<次日>`（有火车则加 `raw/train-*`），≤3 条，按能否解决用户描述的情况排序；
- 用户情况里提到的日期不在脚本覆盖范围时，允许「候选为空 + summary 说明只能查到当日与次日」，不许自己补查；
- 不许承诺免费改签（flyai 无退改签数据）这条保留。

### 4.3 discover

一个字不改。它是唯一还需要 agent 自己理解「缺什么、要不要反问」的路径，也是唯一保留 2 轮重试的路径。

## 5. 密钥口径

| key | 必需性 | 注入点 | 缺失时行为 |
|---|---|---|---|
| `BAILIAN_API_KEY` | 必需 | `opencode.json` 的 `provider.bailian.options.apiKey` = `{env:BAILIAN_API_KEY}`；进程环境 | `missingApiKey()` 直接抛错 → job failed，不重试、不动旧快照 |
| `FLYAI_API_KEY` | 可选 | `agentEnv()` 原样透传（flyai CLI 自己读这个变量；已核 bundle 里 `process.env.FLYAI_API_KEY`） | 脚本不含火车查询，提示词明写不许查火车，`notes` 说明；`meta.mode` 由 raw 是否含「体验模式」判 `trial`，界面照旧标注 |

- 两者都写进 `apps/admin/.env.example`（注释写明来源是 `secrets.env`，不入库）；
- **两者都不进 Joi 校验**：`BAILIAN_API_KEY` 缺失走运行期报错，`FLYAI_API_KEY` 本来就允许缺失。

## 6. replan 入参

```
POST /api/replan
{ "situation": "MF8561 取消了，我 11-06 下午 3 点前必须到上海",
  "flight": { "transport_no": "MF8561", "origin": "北京", "destination": "上海",
              "date": "2026-11-06", "dep_time": "2026-11-06 09:05:00" } }   // 可选
```

- 形状复用 `packages/shared` 的 `InterruptionFlight`，不新造类型；
- 不给 `flight` 时用 `previous.interruption.flight`（现行为）；给了就整块覆盖，5 个字段缺一个即 400；
- 覆盖值必须同时进 `input.json` 的 `previous.interruption.flight` 与脚本参数（航线、日期）；`dep_time` 只进提示词，不进脚本；
- 前端本批不改（`heart.tsx` 仍只传 `situation`），接口向后兼容。

## 9. 验收（逐条当场可验）

| # | 验收项 | 怎么验 |
|---|---|---|
| 1 | 真实 refresh 稳定进 150s 内（目标 120s）且闸门全过 | 起 job 计时；`dataset.json` 5 天齐全、价格全命中 raw；`raw/` 有 6 个 `.json`（有 key 则 7 个） |
| 2 | 一次真实 replan 单轮内 done 且候选 ≤3 条 | 输入「MF8561 取消了，我 11-06 下午 3 点前必须到上海」，计时 < 120s；候选每条价格命中 raw |
| 3 | 无 `FLYAI_API_KEY` 时确实不查火车 | 清掉 key 跑 replan：`raw/` 无 `train-*`，`notes` 有说明，闸门仍过 |
| 4 | 注入被挡 | `origin` 填 `"; rm -rf /tmp/flypig-agent"`，job failed 且错误文案点名城市字段；`/tmp` 下无副作用 |
| 5 | 预算分档生效 | 单测断言三类任务的 `timeoutMs`；把 FakeRunner 换成必抛错，discover 重试 2 次、refresh 1 次 |
| 6 | replan 结构化入参 | 带与快照不同的 `flight` 提交，结果候选航线随入参变化；不带则沿用快照 |
| 7 | 全绿 | `pnpm test` / `pnpm typecheck` / `pnpm lint` / `pnpm build` |

第 1、2 条是本 spec 的完成标准，也是账本第 1 条的完成标准。

## 10. 不做

- refresh / replan 的价格缓存（决策 5）；
- 省心段的结构化行程编辑界面（账本第 3 条，只定契约）；
- 脚本瘦身 SKILL.md（另一条独立杠杆，与本次无关）；
- 多航线、`target_price` 挪后端（账本第 2 条）；
- 真实推送通道、ECS 部署（账本第 4 条）。

## 11. 风险与 shortcut

| 项 | 说明 |
|---|---|
| 脚本 = 后端间接调 flyai | 决策 2 的**受限例外**：脚本只取原始输出，不解析、不判断、不落库；一旦有人往脚本里加 `| jq .min` 之类的处理，这条边界就破了，判据是闸门还能否独立复核 |
| replan 日期覆盖有限 | 只查当日 + 次日。用户说「后天」时结果为空 + 说明，这是有意的取舍，不是 bug；要扩就先看脚本参数怎么从自由文本取日期 |
| 150s 仍由模型轮次决定 | 脚本把查询压到秒级，但「读 raw → 算最低价 → 写产物」还是模型轮次。若实测超 150s，先加 §4.1 的 `node -e` 纪律，仍未达再考虑 180s（单行改动），不要加缓存 |
| flyai 有限流 | 实测 6 条并发触发 `429 Rate limit exceeded`（只放行 2 条）。脚本已改逐条串行；若将来要并发，必须先确认限流额度并加 429 重试 |
| 去掉 refresh/replan 重试 | 失败即 failed，用户得再点一次。旧快照不动，界面有重试按钮，可见代价可接受 |
| 提示词不再教「怎么查」 | agent 在 refresh/replan 上失去自主性。若 flyai 参数变更，脚本会整体失效（错误在 raw 里可见），修法集中在 `query.script.ts` 一处 |
| shortcut | 查询计划在 `query.script.ts` 里手写成两个 `plan*` 函数，没有配置化；只有三类任务、两条路径，等第四条路径出现再抽 |
